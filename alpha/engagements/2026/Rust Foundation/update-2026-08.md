## AI Security Engineer in Residence

Jacob continues his work through the AI Security Engineer in Residence program to expand from scanning and finding generation into remediation, disclosure, and tooling that can make results directly available to maintainers.

Several findings have now become public. Two findings in [`napi-rs`](https://github.com/napi-rs/napi-rs/security) were assessed as high-to-critical severity depending on usage patterns, and the maintainer has requested CVEs:

- [GHSA-qr54-xrr9-7575](https://github.com/napi-rs/napi-rs/security/advisories/GHSA-qr54-xrr9-7575)  
- [GHSA-wrm3-6gmv-vpmw](https://github.com/napi-rs/napi-rs/security/advisories/GHSA-wrm3-6gmv-vpmw)

The maintainer is also triaging more than 40 additional, lower-severity findings in `napi-rs` shared through Scrutineer. Additional public reports and fixes have landed in projects including [`unic-locale`](https://github.com/zbraniecki/unic-locale/pull/86) and ICU4X ([\#8289](https://github.com/unicode-org/icu4x/pull/8289), [\#8285](https://github.com/unicode-org/icu4x/pull/8285)). These results are useful evidence that expanding scans beyond already well-reviewed Rust Project code can surface additional and potentially more significant vulnerabilities.

A self-service Scrutineer sharing site is also now usable at [share.scrutineer.security.rustfoundation.org](https://share.scrutineer.security.rustfoundation.org/). Maintainers can authenticate with GitHub and view findings for repositories where they have commit access, without requiring a Foundation engineer to manually grant access. The current authorization model is intentionally simple and will need to become more sophisticated, but this represents an important step toward making security findings directly accessible to maintainers at scale.

Operational work on Scrutineer continues as well. GitHub OAuth problems affecting access were corrected, and work is underway to improve repository discovery through GitHub's GraphQL API. The team is also working toward a clearer disclosure policy for findings, including what happens when maintainers cannot be reached.

### Scaling AI-assisted scanning

Scanning throughput continues to be constrained by model API limits. Earlier in August, the program had approximately 405 findings awaiting triage, enough to provide weeks of remediation work even without additional scanning. More intensive scanning modes have found roughly five times as many potential bugs while consuming around ten times as many tokens, reinforcing the need for different tiers of analysis.

The Foundation is exploring potentially using local models as a first-pass scanning layer. Rather than attempting full Scrutineer-quality analysis of every package, this layer would focus on high-signal issues such as malware and obviously suspicious code, escalating selected findings to more capable models and human review.

Initial, rough estimates for operating a hosted model across all crates.io publishing activity are approximately $100K–$130K per year in cloud GPU capacity. More recent experimentation from Adam suggests there may also be a quicker path to an initial prototype using existing AWS credits, while a more sustainable and lower-cost architecture could be designed for 2027 and beyond.

## crates.io Malware Detection and Quarantine

The August supply-chain attack involving `arrayref`, `internment`, `append-only-vec`, and led by the malicious `proc-macro1` crate (along with others) has accelerated work around proactive malware detection and crate quarantine.

The [Rust Security Response Working Group's incident report](https://blog.rust-lang.org/2026/08/20/supply-chain-attack-on-arrayref/) describes how the `proc-macro1` crate (along with others) used a build script to download a malicious payload. Some legitimate crates such as arrayref were republished, made to depend on the malicious crate. The affected versions were removed, and the relevant account was locked as a precaution. Thanks to the Research Team at Nextron Systems GmbH for initially discovering the malicious attack and reporting it to us. And thanks to Emily Albini, Manish Goregaokar, Marco Ieni, Tobias Bieniek, Ubiratan Soares, and Walter Pearce for participating in the response here.

Following the incident, work restarted on scanning all crates around publish time for obvious malware. Early experimentation suggests that a first implementation may be practical using existing cloud resources while the team works on the longer-term architecture.

Our new [Foundation Engineer in Residence](https://rustfoundation.org/media/welcoming-jess-izen-as-engineer-in-residence-at-the-rust-foundation/), Jess Izen, has been having discussions with the Cargo team, and they have been receptive to discussing a post-publish quarantine mechanism. Rather than staging every crate before publication, the current direction is to quarantine only packages synchronously identified as suspicious. That model could allow normal publishing to remain fast while giving crates.io a mechanism to temporarily restrict suspicious packages while they are reviewed.

Current next steps include:

- determining how a quarantine mechanism interacts with signing and mirroring;  
- developing the design further with Cargo and [crates.io](http://crates.io) stakeholders;  
- documenting the proposal for broader review; and  
- feeding publish-time malware scanning results into any eventual quarantine system.

Human review remains central to the design: automated scanning is intended to identify and prioritize suspicious packages, not independently delete or block legitimate software without review.

## Build-Time Sandboxing

Adam is progressing on work around sandboxing executable code used during Rust builds.

A new `rustc` wrapper prototype has been developed that can sandbox proc macros independently, with separate configuration for individual proc macros. The approach may be combinable with the [build-script sandboxing](https://www.google.com/url?q=https://rust-lang.zulipchat.com/%23narrow/channel/628857-t-cargo.2Fbuild-script&sa=D&source=docs&ust=1787941934970778&usg=AOvVaw1eTpH_yti0Bs0TXVZ5yA1g) already available through `cackle-rs`, which opens up the possibility of  providing a drop-in tool and Cargo configuration that makes builds sandboxed by default while the Rust Project develops a longer-term native solution.

This work is related to the new Cargo build script working group, involving Foundation and Project contributors, which intends to look at sandboxing as a potential project. It directly complements malware scanning: instead of relying only on detecting malicious build-time behavior after publication, sandboxing can reduce what untrusted proc macros and build scripts are able to do in the first place.

## Signing and Mirroring

The Rust Project's verifiable signing and mirroring Rust Project [goal](https://rust-lang.github.io/goals/2026/mirroring.html) made substantial [progress](https://github.com/rust-lang/goals/issues/637#issuecomment-5281940267) during August, led by Arlo, Walter and those participating in \#tbd-signing.

As a reminder, the goal is to build an MVP for cryptographically verified Rustup and Cargo mirrors using The Update Framework (TUF). The effort is deliberately incremental: deploy alternative mirror infrastructure, validate mirror synchronization using TUF, and then move verification into unstable Rustup and Cargo features once the approach is proven.

Full mirrors of Rust distribution content and crates.io are now available in GCP for experimentation. A test covering approximately 7,000 Rust channel manifests and 170,000 artifacts produced roughly 2.75 MB of TUF metadata. This has helped shift the discussion toward how to keep metadata manageable over time through delegations and archival structures.

Arlo has also been developing an extension to the Rust TUF implementation that adds a DSSE POUF and additional signing algorithms, along with a Rust port of `tuf-on-ci`. The tooling supports GitHub-PR-managed manual signing with YubiKeys, and a working YubiKey signing workflow was demonstrated during the August 20 project meeting.

Current design work includes:

- restructuring nightly artifacts to support TUF delegation  
- exploring archival structures for older nightlies to keep metadata growth manageable  
- using TUF consistent snapshots to support mutable channel aliases such as `stable`;  
- working through how Rustup installation and updates should be validated, including the initial bootstrap problem  
- determining where TUF metadata should live while keeping crates.io and Rust distribution infrastructure separated  
- ensuring mirrors do not serve TUF metadata that is newer than the artifacts they have available, preventing inconsistent or "torn" mirror states

Rustup is expected to be the first client to exercise the new signing and mirror-selection functionality. For crates.io, the team does not plan to put every package version directly into a conventional TUF target repository as the scale and update rate of crates.io require a more scalable verification model.

## Infrastructure Security

Several additional infrastructure-hardening improvements landed during August, led by Marco, Ubi and the Rust Project infrastructure team.

### Audit logs

We enabled [Audit Logs](https://github.com/rust-lang/infra-team/issues/290) for AWS (via [Cloudtrail](https://aws.amazon.com/cloudtrail/)), Wiz, fastly and Datadog, so that the Rust Foundation security team can analyze them in DataDog using [Cloud SIEM](https://www.datadoghq.com/product/cloud-siem/).

### docs.rs WAF

Fastly Next-Gen WAF was enabled for the docs.rs CDN, providing rate limiting and protection against several classes of attacks while also reducing load on the docs.rs origin infrastructure.

Relevant implementation work includes:

- [https://github.com/rust-lang/simpleinfra/pull/1149](https://github.com/rust-lang/simpleinfra/pull/1149)  
- [https://github.com/rust-lang/simpleinfra/pull/1165](https://github.com/rust-lang/simpleinfra/pull/1165)  
- [https://github.com/rust-lang/simpleinfra/pull/1177](https://github.com/rust-lang/simpleinfra/pull/1177)  
- [https://github.com/rust-lang/simpleinfra/pull/1179](https://github.com/rust-lang/simpleinfra/pull/1179)  
- [https://github.com/rust-lang/simpleinfra/pull/1180](https://github.com/rust-lang/simpleinfra/pull/1180)

### Trusted publishing

Two crates released from the docs.rs repository (`docs-rs-crates-io` and `font-awesome-as-a-crate`) have been moved to crates.io trusted publishing, reducing reliance on long-lived publishing credentials.

### Automated dependency maintenance

Renovate has been configured for `rust-lang/rust` to automatically propose updates to Cargo lockfiles and GitHub Actions and to address dependency security findings. The minimum Python version supported by the repository's Tidy tooling was also manually moved away from Python 3.9 after its end of life to Python 3.11.

### Hardware-backed authentication

Support was added for storing PIV-related YubiKey attestation certificates in `rust-lang/team`, allowing certificates to be validated against the Project's inventory of hardware keys.

The Foundation is also continuing its broader hardware-key rollout across infrastructure services. Roughly half of those with AWS infrastructure access had completed YubiKey setup by mid-August, with continued follow-up underway. Infrastructure tooling such as Ansible and Terraform can now operate through SSO sessions protected by hardware-key authentication.

The Foundation also plans to require hardware-key or passkey authentication for Google Workspace rather than allowing password-only access.

## Crabwatch

The Infrastructure team's 2026 Outreachy project concluded with a minimum viable version of [Crabwatch](https://www.google.com/url?q=https://github.com/rust-lang/crabwatch&sa=D&source=docs&ust=1787905494995721&usg=AOvVaw3Pd2VL7sUjBV5BigjFm3xE).

Crabwatch is intended to provide centralized auditing of GitHub Actions across Rust Project repositories. It gives the Infrastructure team a mechanism to detect common CI security problems consistently and incrementally roll those checks out across Project repositories.

The MVP has been expanded and introduced to additional `rust-lang` repositories, running in 28 repos as of now.
